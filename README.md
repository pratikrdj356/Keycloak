# Keycloak on Local Kubernetes — Pulumi (Go) IaC

Fully automated, reproducible deployment of Keycloak on a local Kubernetes cluster,
provisioned with k3d (Rancher's k3s-in-Docker distribution) and configured entirely
through Pulumi + Go. Tested end-to-end on macOS (Apple Silicon).

## What this deploys

| Component | Purpose |
|---|---|
| **k3d cluster** | Local Kubernetes control plane + 2 agents, Traefik disabled |
| **ingress-nginx** | Ingress controller, terminates at the load balancer on 80/443 |
| **cert-manager** (Helm `Release`) | Issues TLS certificates for the ingress |
| **ClusterIssuer (self-signed)** | Local substitute for a real CA / Let's Encrypt |
| **Keycloak** (Helm `Release`, Bitnami chart, bundled Postgres) | The application itself |
| **`admin` account** | Generated via `pulumi-random`, stored in a Kubernetes Secret, never hard-coded |
| **NetworkPolicy** (default-deny + allow-from-ingress-nginx) | Keycloak pods only accept traffic from the ingress controller |

## Prerequisites

Install all of these **before** running anything:

| Tool | Check | Install (macOS) |
|---|---|---|
| Docker (running, not just installed) | `docker info` | https://www.docker.com/products/docker-desktop/ — launch it once after installing |
| `kubectl` | `kubectl version --client` | `brew install kubectl` |
| `helm` | `helm version` | `brew install helm` |
| Pulumi CLI | `pulumi version` | `brew install pulumi` |
| Go ≥ 1.21 | `go version` | `brew install go` |

`k3d` itself does **not** need to be pre-installed — the setup script installs it
automatically on first run if it's missing.

**Resource note:** allocate Docker Desktop ≥ 6 GB RAM (Settings → Resources) before
starting — a 3-node k3d cluster plus Keycloak plus bundled Postgres will stall on the
2 GB default.

## Setup — single command

```bash
git clone https://github.com/pratikrdj356/Keycloak.git
cd Keycloak
./scripts/setup.sh
```

That one script does everything: checks prerequisites, creates the cluster, deploys
Keycloak via Pulumi, adds the `/etc/hosts` entry (will prompt for your sudo password
once), and prints the login URL and admin credentials at the end. Takes roughly
4–6 minutes on a first run (image pulls).

Then open **https://keycloak.local** in a browser (accept the self-signed cert
warning) and log in with the credentials printed at the end of the script.

### Running the steps individually (optional)

If you'd rather run each stage yourself instead of the single `setup.sh`:

```bash
./scripts/00-create-cluster.sh   # k3d cluster + ingress-nginx
./scripts/01-deploy.sh           # pulumi up — cert-manager + Keycloak
echo "127.0.0.1 keycloak.local" | sudo tee -a /etc/hosts
pulumi stack output keycloakAdminPassword --stack dev --show-secrets
```

## Teardown

```bash
./scripts/02-teardown.sh
```
Destroys all Pulumi-managed resources and deletes the k3d cluster.

## Security / hardening notes

- **HTTPS everywhere**: cert-manager issues a TLS cert bound to `keycloak.local`;
  the ingress redirects HTTP → HTTPS, and Keycloak runs with `proxy=edge` so it only
  trusts `X-Forwarded-*` headers coming from the ingress, not the public internet.
- **Minimal exposure**: Keycloak's Service is `ClusterIP` only, reachable exclusively
  through the ingress. A `NetworkPolicy` default-denies all ingress traffic to the
  namespace, then explicitly allows only traffic from the `ingress-nginx` namespace.
- **No hard-coded secrets**: the admin password is generated by `pulumi-random`,
  written into a Kubernetes `Secret`, and referenced by the Helm release via
  `existingSecret` — it never appears in source control.
- **Non-root containers**: `runAsNonRoot: true`, `allowPrivilegeEscalation: false`
  on the Keycloak pod's security context.
- **Resource limits** set on the Keycloak deployment.

## Assumptions & real issues hit (and fixed) during testing

Documenting these because they're genuine gotchas a fresh clone can still hit
depending on when it's run, not just theoretical risks:

- **"Rancher preferred" → k3d.** k3d is Rancher's own k3s-in-Docker tool and is
  fully scriptable end-to-end; a full Rancher Desktop install would add manual UI
  steps that work against "fully automated." Swap `scripts/00-create-cluster.sh`
  if a different distribution is specifically required — `main.go` itself is
  distribution-agnostic (Pulumi's `kubernetes` provider just reads the active
  kubeconfig context).
- **Bitnami image catalog restructuring (Aug 2025).** Bitnami moved its full free
  image catalog from `docker.io/bitnami/*` to `docker.io/bitnamilegacy/*` as part
  of a push toward a paid "Secure Images" subscription. `main.go` explicitly
  overrides the Keycloak and Postgres image repositories to `bitnamilegacy/*` and
  sets `global.security.allowInsecureImages: true`, which current Bitnami charts
  require whenever the registry isn't the chart's default. If Bitnami relocates
  the catalog again, this is the block in `main.go` to update.
- **Helm resource type matters.** `main.go` uses Pulumi's `helm.v3.Release`
  (a real `helm install` against the live cluster) rather than `helm.v3.Chart`
  (client-side template rendering). `Chart` was observed failing with a
  `kubeVersion` incompatibility because it couldn't correctly detect the live
  cluster's Kubernetes version during local rendering; `Release` reads it from
  the real API server and doesn't have this problem.
- **Self-signed TLS**, not a browser-trusted cert — acceptable for a local
  assignment environment. Swapping the `ClusterIssuer` for `acme`/Let's Encrypt
  is a small, isolated change if a publicly resolvable domain is available.
- **Bundled Postgres** subchart is used instead of an external managed database,
  for reproducibility in a local, ephemeral environment.
- **Pulumi state is local** (`file://./.pulumi-state`), so the whole exercise
  requires no external Pulumi Cloud account.
